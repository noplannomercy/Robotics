# 역문서엔진 MVP — 의존성 순서 현상 파악 (설계)

> 작성일: 2026-06-16
> 상태: 승인됨 (brainstorming 결론)
> 관련: `HCA_Code2Rule/역문서엔진설계변경.md`, 적대적 감사 `dynamicWorkflow/docs/reverse_doc_loop_adversarial_review.md`, `Robotics/TODO.md`

---

## 1. 목적

Oracle PL/SQL 1,800패키지를 **의존성 순서로 한 번 역문서화하여 LightRAG에 적재**하고,
**현상(역문서 품질·빈약한 부분)을 눈으로 파악**한다. 완벽한 검증 루프가 아니라 **직관적 최소형이 우선.**

## 2. 배경 — 왜 분석 결과를 빼는가

적대적 감사가 지적한 Outer 루프·파킹·재트리거·graph_epoch 등은 **의존성 순서 적재로 대부분 불필요**해진다:
- 의존성 순서(바텀업)로 넣으면 **"X가 호출하는 것(callee)"은 X 처리 시점에 이미 그래프에 있음** → 자연 해결.
- 남는 건 "X를 호출하는 것(caller)" 정보뿐인데, 이는 **현상 파악 단계에선 비어도 수용**.
- 따라서 복잡한 수렴 기계는 **현상을 본 뒤 필요성이 입증되면** 도입한다(현재 보류).

## 3. 범위

**IN (이번 MVP)**
- 의존성 순서 정렬 (DDL/딕셔너리 → 말단 SQL → 상위 SQL)
- 순서대로 기존 **생성 모드**로 역문서 1회 생성
- LightRAG 적재 (그래프 자생)
- 결정론 검증 **기준 1·2만** (Inner 루프 — 이미 구현, 2026-06-16 버그 수정 완료 `9d26a79`)
- 결과 품질 **수동 관찰**

**OUT (보류 — `TODO.md` deferred)**
- Outer 루프 / 파킹 / 재트리거 / graph_epoch / caller back-fill
- 기준 3(호출자 인터페이스) · 4(용어충돌) · 5(보완필요항목) 검증
- 비용/예산 게이트

## 4. 아키텍처 / 데이터 흐름

```
[의존성 데이터 (DBA_DEPENDENCIES, 선별 완료분)]
        ↓  위상 정렬(topological sort)
[순서 큐: DDL → 말단 → ... → 상위]
        ↓  순차 투입 (기존 Pylon→Robotics 경로 또는 배치 피드)
[Robotics 생성 모드 = to_reverse_doc]
   - RAG 조회(현재까지 적재분) → 생성 → Inner 검증(기준1·2) → 최선버전 저장
        ↓
[LightRAG 적재]  ← callee 컨텍스트 자생
        ↓
[현상 관찰]  역문서 품질, 빈약한 섹션(특히 호출자), 검증 통과율 기록
```

## 5. 구성 요소 (단위)

1. **의존성 순서 정렬기** — 선별된 의존성 데이터를 위상 정렬해 순서 큐 생성. (입력: 의존성 목록 / 출력: 정렬된 패키지명 리스트 / 의존: 선별 산출물 `03_Phase1_데이터준비`)
2. **순차 적재 드라이버** — 순서 큐대로 패키지 바디를 Robotics에 투입. (기존 `to_reverse_doc` 파이프라인 재사용, 신규 코드 최소)
3. **관찰 기록** — 적재 후 역문서 샘플 품질·빈약 지점·기준1·2 통과율을 수동 기록.

## 6. 성공 기준 (측정 가능)

- 대상(1,800 또는 합의된 서브셋)이 **의존성 순서로** 역문서화되어 LightRAG에 적재됨.
- 각 역문서가 기존 Inner 검증(기준1·2)을 통과(또는 최선버전 저장)한다.
- **현상 관찰 기록 산출**: 무엇이 잘 되고(callee 맥락), 무엇이 빈약한지(caller 등) 1건 문서화.

## 7. 보류 항목의 향방

현상 관찰이 "caller 정보 부재가 실제로 아프다"를 입증하면 → `TODO.md`의 deferred(Outer/back-fill)에서 꺼내 도입. **관찰이 근거를 줄 때까지 만들지 않는다.**
